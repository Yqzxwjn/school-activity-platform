# 源代码说明

学校活动在线服务平台 V1.0 的代码组织、数据模型、接口与关键算法说明，用于开发交接、软件著作权源程序整理与技术复核。

## 一、总体结构

平台是 B/S 架构的前后端一体应用：Node.js 服务端负责鉴权、业务规则与数据持久化，浏览器端为原生 JavaScript 单页应用。

| 层次 | 文件 | 职责 |
| --- | --- | --- |
| 入口 | `server.js` | 启动 HTTP 服务、初始化数据库、托管静态资源、优雅退出 |
| 路由 | `server/api.js` | 接口路由表、会话解析、角色校验、同源校验、统一错误响应 |
| 业务 | `server/services.js` | 活动、报名、候补、签到、审核、账号、统计的业务规则 |
| 数据 | `server/db.js` | SQLite 连接、建表、行映射、种子数据写入 |
| 认证 | `server/auth.js` | scrypt 密码散列、会话令牌、登录失败限流 |
| 工具 | `server/http.js` | JSON 响应、Cookie、请求体解析、静态文件 |
| 数据脚本 | `server/seed.js`、`server/seed-data.json` | 初始化 / 重置演示数据 |
| 前端 | `public/` | 官网、登录、工作台、条款页、样式与脚本 |
| 测试 | `tests/api.test.js` | 启动真实服务进程的接口集成测试 |

## 二、数据库

数据库为 SQLite，文件默认位于 `data/app.db`，启用 WAL 与外键约束。表结构：

```
users (id PK, name, account UNIQUE, password_hash, role, class_name, grade,
       phone, title, department, status, created_at)

activities (id PK, title, category_id, organizer_id FK→users,
            location, target, capacity, start_at, end_at, reg_deadline,
            created_at, updated_at, cover_tone, summary, description,
            agenda_json, notice_json,
            review_status, review_at, review_by, review_reason)

registrations (id PK, activity_id FK→activities ON DELETE CASCADE,
               user_id FK→users, name, class_name, grade, phone, note,
               status, code, created_at, checked_at,
               UNIQUE(activity_id, code))

notices (id PK, user_id FK→users, type, title, body, activity_id, created_at, read_at)

sessions (token PK, user_id FK→users, created_at, expires_at)

meta (key PK, value)
```

关键约束与索引：

- `registrations` 上建立部分唯一索引 `(activity_id, user_id) WHERE status <> 'cancelled'`，保证同一活动同一账号只有一条有效报名，取消后可以重新报名。
- `(activity_id, code)` 唯一，保证签到码在活动内不重复。
- `activities(organizer_id)`、`activities(review_status)`、`registrations(activity_id, created_at)`、`notices(user_id, created_at)` 建立索引。

枚举：

- `users.role`：`student` 学生、`organizer` 活动组织者、`admin` 管理员。
- `users.status`：`active` 正常、`disabled` 停用。
- `activities.review_status`：`draft` 草稿、`pending` 待审核、`approved` 已通过、`rejected` 已驳回。
- `registrations.status`：`confirmed` 已报名、`waitlist` 候补、`checked` 已签到、`cancelled` 已取消。
- `notices.type`：`signup` 报名、`review` 审核、`reminder` 提醒、`system` 系统。

## 三、关键算法

### 1. 活动状态推导

状态不落库，由审核状态与当前时间实时计算（`services.statusOf`）：

```
review_status = draft      → 草稿
review_status = pending    → 待审核
review_status = rejected   → 已驳回
now < reg_deadline         → 报名中
now < start_at             → 报名截止
now <= end_at              → 进行中
否则                        → 已结束
```

活动过期不需要定时任务改数据，打开页面即为最新状态。

### 2. 名额与候补

`registrationStats` 用一条聚合 SQL 得到正式名额、候补人数与已签到人数：

```
confirmed = count(status in ('confirmed','checked'))
waitlist  = count(status = 'waitlist')
left      = max(0, capacity - confirmed)
```

报名在 `BEGIN IMMEDIATE` 事务中完成：

1. 校验活动已通过审核且处于报名中。
2. 查询同一活动同一账号的有效报名，存在则返回 409。
3. 重新统计正式名额，判断写入 `confirmed` 还是 `waitlist`。
4. 生成 6 位签到码，与活动内已有签到码比对，冲突则重新生成（最多 30 次）。
5. 写入报名记录与站内通知；如果这是最后一个名额，额外通知组织者。

取消报名同样在事务中进行：先记录原状态，取消后若释放的是正式名额，取候补队列中 `created_at` 最早的一条转为 `confirmed`，并给对方写入「候补递补成功」通知。

### 3. 签到核销

`checkInByCode` 按「活动 + 签到码」定位有效报名：

- 签到码格式不合法 → 400。
- 记录不存在 → 404。
- 已核销 → 409，并返回首次核销时间。
- 候补状态 → 409，提示未获得正式名额。
- 正常 → 写入 `checked` 与签到时间，返回报名人与活动最新统计。

`checkInById` / `undoCheckIn` 供组织者在名单中手动核销与撤销。

### 4. 审核流转

- 组织者保存 → `draft`。
- 提交审核 → `pending`，向所有在职管理员写入待审核通知。
- 管理员通过 → `approved`，活动立即出现在活动广场，通知组织者。
- 管理员驳回 → `rejected`，必须附至少 6 个字的理由，通知组织者。
- 编辑已通过的活动 → 保存时重新进入 `pending`，避免未审核内容直接对外展示。

### 5. 统计口径

`buildStats` 按以下口径计算：

- 已上架活动数、可参与活动数（报名中或进行中）。
- 报名人次（不含已取消）、已签到人次、候补人次、待审核数。
- 平均签到率：只对已结束活动计算 `已签到 / 正式报名`，避免未开始活动拉低比例。
- 近 6 个月报名趋势：按报名时间的年月分组。
- 分类分布、年级分布、热门活动排行（前 6 场，附签到率与是否结束）。

### 6. 场地冲突检测

发布表单与审核页都会检测：排除自身、只比较已通过审核的活动、地点相同且时间区间相交（`start < other.end && end > other.start`）。命中时提示但不强制阻止，由管理员最终判断。

## 四、接口与权限

接口采用同源 Cookie 会话（`sid`，HttpOnly、SameSite=Lax、7 天过期）。每个请求解析会话并校验账号状态；写操作额外校验 `Origin` 与 `Host` 一致。

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| POST | `/api/auth/login` | 公开（同一 IP + 账号 10 分钟 8 次失败限流） |
| POST | `/api/auth/logout` | 公开 |
| GET | `/api/auth/me` | 公开（未登录返回 `user: null`） |
| POST | `/api/auth/password` | 登录用户 |
| GET | `/api/bootstrap` | 登录用户 |
| GET | `/api/activities`、`/api/activities/:id` | 登录用户（未上架活动仅组织者与管理员可见） |
| POST | `/api/activities` | 组织者、管理员 |
| POST | `/api/activities/:id/submit` | 活动组织者、管理员 |
| DELETE | `/api/activities/:id` | 活动组织者、管理员 |
| POST | `/api/activities/:id/review` | 管理员 |
| POST | `/api/activities/:id/registrations` | 登录用户 |
| DELETE | `/api/registrations/:id` | 本人、活动组织者、管理员 |
| GET | `/api/activities/:id/roster` | 活动组织者、管理员 |
| POST | `/api/activities/:id/checkin` | 活动组织者、管理员 |
| POST / DELETE | `/api/registrations/:id/checkin` | 活动组织者、管理员 |
| GET | `/api/notices`、`POST /api/notices/read` | 登录用户 |
| GET / POST | `/api/users` | 管理员 |
| PATCH | `/api/users/:id` | 管理员 |
| POST | `/api/users/:id/password` | 管理员 |
| GET | `/api/stats` | 管理员 |
| GET | `/api/health` | 公开 |

权限三层：前端导航按角色渲染、路由层校验角色、业务层再次校验数据归属（例如只能修改自己发布的活动）。

## 五、前端实现要点

- 工作台为哈希路由单页应用：`#/square`、`#/activity/:id`、`#/mine`、`#/manage` 等。
- 登录后 `GET /api/bootstrap` 一次取回当前角色可见的活动、报名、通知、账号目录（管理员另有全部账号与统计），保存在内存缓存中；视图同步读取缓存渲染。
- 写操作调用接口后重新拉取缓存或就地更新，再触发当前页面重绘；接口返回 401 时自动回到登录页。
- 表单错误内联展示；确认类操作使用确认弹层；通知角标随未读数量更新。
- 所有页面适配 390px 宽度，移动端侧边栏为抽屉式。

## 六、安全措施

- 密码：scrypt（N=16384, r=8, p=1）加 16 字节随机盐，散列格式 `scrypt$N$r$p$salt$hash`，校验使用 `timingSafeEqual`。
- 会话：32 字节随机令牌，数据库只保存 SHA-256 哈希；停用账号或重置密码会清除该账号全部会话。
- 登录限流：同一 IP + 账号 10 分钟内失败 8 次返回 429。
- CSRF：Cookie 为 SameSite=Lax，写操作校验 Origin 与 Host。
- 静态目录做路径规范化校验，阻止目录穿越。
- 响应头设置 `X-Content-Type-Options`、`X-Frame-Options: DENY`、`Referrer-Policy`。
